# Event Contract v1

v1 实现 Kafka raw click / activation 到无原始身份标准事件的确定性转换。平台注册、付费和退款不属于本版本；后续事件不能通过向 v1 JSON 静默加字段实现。

对应机器可读 Schema：

- [`raw-click-v1.schema.json`](raw-click-v1.schema.json)
- [`raw-activation-v1.schema.json`](raw-activation-v1.schema.json)

## Topic 与访问边界

| Topic | Kafka key | 数据边界 |
|---|---|---|
| `game-attribution.raw.click.v1` | `payload.click_id` | 含原始身份值，受限访问 |
| `game-attribution.raw.activation.v1` | `payload.activation_id` | 含原始身份值，受限访问 |
| `game-attribution.standard.click.v1` | `click_id` | 只含哈希身份，后续 Sink |
| `game-attribution.standard.activation.v1` | `activation_id` | 只含哈希身份，后续 Sink |
| `game-attribution.normalization.invalid.v1` | `topic-partition-offset` | 结构化隔离信息，不含原始 value |

当前代码实现前两条 raw Source、标准化输出流和隔离 Side Output；Kafka Sink 在下一切片实现。

点击与激活使用独立 Source 和 consumer group。正常作业显式使用 committed offset（不存在时 earliest）；历史重放必须使用新的 group ID，并显式选择 earliest 或 timestamp。Flink 从 Checkpoint 恢复时仍以 Checkpoint 中的 split offset 为准。
`NormalizeTopology.attach` 要求调用者先启用 Flink Checkpoint；Kafka auto commit 被关闭，`read_committed` 和 checkpoint offset commit 被固定，两个 Source 也使用不同 `client.id.prefix`。

## Raw envelope

公共字段：

| 字段 | 类型 | 约束 |
|---|---|---|
| `schema_version` | integer | 当前只能为 `1` |
| `event_id` | string | 上游生成的稳定幂等键，最长 128 |
| `event_type` | string | `click` 或 `activation`，必须与 Topic 一致 |
| `event_time` | int64 | UTC Unix epoch milliseconds，业务发生时间 |
| `ingest_time` | int64 | 首次可信采集时间，重放时不能重写 |
| `tenant_id` | string | 发行主体范围 |
| `game_id` / `app_id` | string | 游戏和应用范围 |
| `source_system` | string | 产生数据的采集系统，如 `gdt_click_collector` |
| `client_platform` | string | 游戏运行端，如 `wechat_mini_program`、`android` |
| `payload` | object | 事件专有字段 |

`platform` 不再同时表示运行端和广告网络。点击的广告平台使用 `payload.ad_platform`，最终映射到 `CampaignRef.platform`。

Click payload：

```json
{
  "click_id": "clk_v1_...",
  "ad_platform": "gdt",
  "identities": [{"type": "oaid", "value": "raw-source-value"}],
  "campaign": {
    "account_id": "account-1",
    "campaign_id": "campaign-1",
    "ad_group_id": "group-1",
    "creative_id": "creative-1"
  },
  "eligible": true
}
```

Activation payload：

```json
{
  "activation_id": "act_v1_...",
  "install_id": "install-1",
  "direct_click_id": "clk_v1_optional-fast-path",
  "identities": [{"type": "openid", "value": "raw-source-value"}]
}
```

`direct_click_id` 可省略；`install_id` 必填，用于后续 `install_attribution_current` 主键映射。
`event_id`、`click_id`、`activation_id` 和 `install_id` 都必须是 namespaced opaque ID，不能直接使用手机号、OpenID、OAID、IDFA 或账号名。
`StandardActivationEvent.toCoreEvent()` 只是归因评分所需的窄视图；后续 Lookup 和结果物化必须继续携带原标准事件，不能丢失 `install_id` / `direct_click_id`。

## Kafka key 与稳定 ID

Kafka key 必须是 UTF-8，且与 payload 中的 `click_id` / `activation_id` 完全一致。这样同一业务事件的重复投递稳定进入同一分区；点击与激活之间不能依赖跨 Topic 顺序。

仓库提供 `StableEventIds`，使用不可歧义的长度前缀编码：

```text
LP(s) = uint32_be(length(UTF8(s))) || UTF8(s)

click_id = "clk_v1_" + base64url_no_padding(
  SHA-256(LP(namespace) || LP(tenant) || LP(game) || LP(app)
    || LP(ad_platform) || LP(upstream_click_id)))

activation_id = "act_v1_" + base64url_no_padding(
  SHA-256(LP(namespace) || LP(tenant) || LP(game) || LP(app)
    || LP(client_platform) || LP(upstream_activation_id)))
```

算法、字段顺序和 namespace 在 v1 生命周期内不可修改。跨语言黄金向量已经固化在 `StandardEventTest`。
`upstream_click_id` / `upstream_activation_id` 必须是平台提供的 opaque event identifier，不能是 OpenID、OAID、IDFA 等玩家标识；若来源 ID 可枚举或含玩家信息，ID 生成也必须改用版本化 HMAC。

## Source position

`source_position` 不得由 producer 写入 JSON。Topic、partition、offset、Kafka record timestamp 和 timestamp type 只在 broker 写入后成立，因此由 `KafkaInputRecordDeserializationSchema` 从 `ConsumerRecord` 注入：

```text
topic / partition / offset / record_timestamp / timestamp_type
```

Kafka timestamp 只用于链路审计，Kafka timestamp 不参与归因排序。当前标准化作业无状态，因此不生成 Watermark；下一步从 standard Topic 读取时，必须在 Kafka Source 内从标准事件的 payload `event_time` 分配每分区 Watermark，并配置 bounded out-of-orderness 与 idleness。不能在 Kafka Source 合并分区之后才统一生成 Watermark，否则会丢失每分区进度语义。

Offset 只用于审计、重放和隔离定位，不参与候选 tie-break 或业务幂等键。

## 身份规范化

Raw value 只允许出现在受限 raw topic。标准事件输出排序后的：

```json
{
  "type": "oaid",
  "value_hash": "64-lowercase-hex",
  "normalization_version": "game-attribution-identity-v1",
  "key_version": "unkeyed-placeholder-v1"
}
```

- Canonicalization 由 `ConfiguredIdentityNormalizationPolicy` 按 identity type 选择，raw JSON 无权指定；每条规则必须同时声明 `normalization_version` 和 `key_version`，改变规则或密钥必须升级对应版本。
- 当前 scoped SHA-256 只是可运行的学习占位实现，仍是 pseudonymous data；生产接入必须改成密钥服务提供的 scoped HMAC，并升级 `key_version`。
- 摘要输入使用长度前缀，包含 tenant、game、app 和 identity type。
- 标准 identity 按 `(type, value_hash, normalization_version, key_version)` 排序，输入数组顺序不会改变输出。
- 单个身份无效时，保留其他有效身份并输出 `IdentityNormalizationIssue`；全部无效才隔离整条事件。
- 原始 OpenID、OAID、IDFA、设备标识和 raw payload 不得进入标准 Topic、普通日志或 `RejectedRecord`。

## Strict decode 与失败语义

v1 解码器限制 64 KiB payload、16 层 JSON、4 KiB 单字符串和最多 16 个身份。以下错误生成稳定 `RejectionCode`：

- null key/value、非法 UTF-8、过大消息；
- malformed JSON、重复字段、trailing token；
- 缺字段、类型不符、未知字段；
- 未知 `event_type` / `schema_version`；
- Topic 与 event type 不一致；
- Kafka key 与业务 ID 不一致；
- 时间、ID 或身份不变量失败。

`RejectedRecord` 只包含 source position、payload SHA-256、payload 大小、错误码和预定义安全字段路径。已知数据错误不会抛出导致 poison-pill 重启；编程错误、Collector/Sink 失败、OOM 和基础设施异常仍让 Flink 作业失败恢复。

一旦坏消息被转换成普通 Side Output，Checkpoint 可以继续推进输入 offset，因此生产拓扑必须把隔离流持久化。若合规要求保存原文，应写入加密、短保留、严格 ACL 的隔离存储，不能放在普通错误表。

## Schema evolution

- v1 Schema 使用 `additionalProperties: false`，不通过 `@JsonAlias` 或忽略未知字段掩盖漂移。
- 新 consumer 先同时支持旧、新版本，再发布 producer。
- 字段删除/重命名、类型/单位/语义改变、Key 算法改变属于 breaking change，创建 `.v2` Topic。
- `schema_version` 的新值在当前解码器中进入隔离，升级后可按 source position 重放。
- Wire DTO 应尽快转换为标准领域模型，不能直接成为长期 Flink State key。
- `event_time`、`ingest_time`、7 天 lookback、乱序 Watermark 和归因 grace 是不同概念，不能互相替代。
